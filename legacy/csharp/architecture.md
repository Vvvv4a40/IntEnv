# Архитектура файлов Envi v0.1

Это схема уже созданной основы, а не только желаемого проекта. Один процесс Windows, два логических слоя: окно и независимое ядро. Groq — внешний сервис, не локальная нейросеть. Слои разделены, чтобы добавлять возможности по одному модулю и проверять логику без микрофона, сети и запуска приложений.

## Дерево проекта

```text
Envi/
├─ README.md                       Как запустить и проверить
├─ start.ps1                       Запуск с настройками из корня проекта
├─ verify.ps1                      Сборка + тесты + проверка инициализации окна
├─ envi.settings.json              Модели, лимиты, разрешённые цели
├─ Envi.slnx                       Объединяет три .NET-проекта
├─ Directory.Build.props           Общие настройки компиляции
├─ NuGet.Config                    Без внешних пакетов в базовой версии
├─ .gitignore                      Не сохранять сборки и файлы секретов в Git
├─ context.md                      История и подтверждённые решения
├─ concept.md                      Концепция, ограничения и развитие
├─ docs/
│  └─ architecture.md              Эта схема
├─ research/
│  └─ open-source-bases.md          Предыдущее исследование готовых основ
├─ src/
│  ├─ Envi.Desktop/                Windows-интерфейс и микрофон
│  │  ├─ Envi.Desktop.csproj        Сборка WPF-приложения
│  │  ├─ App.xaml                  Объявление приложения
│  │  ├─ App.xaml.cs               Загрузка настроек и соединение компонентов
│  │  ├─ MainWindow.xaml           Разметка окна: ввод, диалог, кнопки
│  │  ├─ MainWindow.xaml.cs        События кнопок, отмена, подтверждения
│  │  └─ Audio/WaveRecorder.cs     Микрофон Windows → WAV в памяти
│  └─ Envi.Core/                   Логика, не зависящая от окна
│     ├─ Envi.Core.csproj          Сборка библиотеки ядра
│     ├─ Contracts.cs             Форматы сообщений и границы модулей
│     ├─ AssistantService.cs      Управляющий цикл одного запроса
│     ├─ Configuration/
│     │  └─ AppSettings.cs         Загрузка и проверка JSON-настроек
│     ├─ Routing/
│     │  └─ RuleRouter.cs          Точные простые команды без LLM
│     ├─ Providers/
│     │  └─ GroqClient.cs          HTTP-клиент STT + LLM, ошибки и лимит
│     ├─ Tools/
│     │  └─ ToolRegistry.cs        Каталог, проверки и исполнение действий
│     └─ Logging/
│        └─ JsonEventLog.cs        Технический журнал без текста/ключа/аудио
└─ tests/
   └─ Envi.Tests/                  Автономные тесты + подставные модель/HTTP
```

Папки `bin/` и `obj/` появляются при сборке: их не редактируем. `.csproj` — описание отдельного проекта; `.slnx` — объединение проектов, а не исполняемый код. `.xaml` задаёт внешний вид окна; соседний `.xaml.cs` — его поведение. Файлы `.cs` содержат C#-код.

## Кто кому передаёт запрос

```text
MainWindow — текст от клавиатуры
     │
     ├─ голос: WaveRecorder → GroqClient.TranscribeAsync → поле ввода
     │                                                     │
     │                                  пользователь проверяет и отправляет
     ▼
AssistantService
     ▼
RuleRouter
     ├─ точная знакомая команда ────────────────┐
     └─ остальное → GroqClient.CompleteAsync    │
                         ├─ обычный ответ → окно
                         └─ предложение инструмента
                                               ▼
                                       ToolRegistry.Validate
                                               ▼
                                подтверждение в MainWindow
                                     (кроме чтения времени)
                                               ▼
                                  ToolRegistry.ExecuteAsync
                                     ├─ локальный запрос → ответ в окно
                                     └─ запрос модели → результат обратно
                                         в модель → окончательный ответ
```

`JsonEventLog` получает технические события из управляющего цикла. Он не участвует в выборе команды и не служит долговременной памятью диалога.

## Главные обязанности

**App.xaml.cs — сборка приложения из деталей.** Читает JSON и `GROQ_API_KEY` из окружения, создаёт один HTTP-клиент, Groq-клиент, реестр действий, журнал и управляющий сервис, передаёт их окну. Ключ не содержится в настройках.

**MainWindow — общение с человеком.** Запускает и останавливает запись, показывает текст и состояние, вызывает ядро, спрашивает согласие на точную цель действия. Окно не придумывает команды и не исполняет произвольный ответ модели. Один запрос обрабатывается за раз.

**WaveRecorder — только запись.** Использует Windows WinMM, записывает 16 kHz / 16-bit / mono PCM, оборачивает его в WAV. Максимум 30 секунд; файл остаётся в оперативной памяти. Нет постоянного прослушивания и распознавания слова активации.

**RuleRouter — дешёвый локальный путь.** Сопоставляет полные однозначные фразы про время, папку проекта, Блокнот, Калькулятор и VS Code. «Не открывай блокнот», вопросы о команде и составные фразы не совпадают с правилом. Это не обученный классификатор. Если был голосовой ввод, его STT уже использовал API, даже когда дальнейшая команда локальна.

**AssistantService — диспетчер.** Выбирает локальный/облачный путь, ведёт ограниченную историю, отправляет сообщения модели, проверяет весь предложенный набор вызовов до действий. Для набора открытий сначала получает все подтверждения; отказ отменяет текущий набор. Проверяет повторные ID и повторные цели, ограничивает число раундов, учитывает отмену. При позднем сбое сообщает о действиях, которые уже успели выполнить; они не откатываются. Вместе с итогом модели показывает фактические результаты запусков.

**GroqClient — сменяемая интеграция с облаком.** Отправляет только на два фиксированных HTTPS-адреса Groq. Чат получает сообщения и схемы функций, возвращает текст либо структурированные вызовы. STT получает WAV и возвращает русский текст. Клиент ограничивает длительность ожидания и число отправок; 429, ошибки ключа и сети превращает в понятные сообщения, без автоматического повтора.

**ToolRegistry — граница полномочий.** Есть лишь `get_time`, `open_app(app)` и `open_folder(folder)`. `app` и `folder` — имена из разрешённых списков JSON, не произвольные пути от модели. Проверяются формат, отсутствие лишних/повторных полей, типы, имена, существование целей. Проверка повторяется при исполнении. Командные оболочки заблокированы; дополнительных аргументов запуска нет. Настройки — доверенный пользовательский файл, не песочница для произвольных сторонних программ.

## Почему ядро отделено от окна

`Envi.Desktop → Envi.Core`, а не наоборот. Ядро не знает о кнопках WPF. `IModelClient` позволяет в тестах заменить модель; `IToolRegistry` — заменить исполнитель без реального запуска приложений; `IEventSink` — заменить журнал. Подтверждение ядро запрашивает через переданную функцию, а окно показывает диалог.

Это **один процесс**, не два сетевых сервиса. Отдельная библиотека ядра не означает backend в WSL. Само ядро можно тестировать без WPF; запуск Windows-программ всё равно привязан к Windows.

## Куда добавлять следующие возможности

| Возможность | Место изменения |
| --- | --- |
| Другая модель Groq, лимиты или ещё одна разрешённая папка | `envi.settings.json`; затем перезапуск |
| Ещё одна локальная точная фраза | `RuleRouter.cs` + тесты |
| Новый тип действия, например громкость | Отдельный обработчик в `Tools/`, схема/проверки в реестре + тесты |
| Другой провайдер LLM | Новый `IModelClient` в `Providers/`, подключение в `App.xaml.cs` |
| Python-скрипт/Playwright | Отдельный ограниченный инструмент/адаптер, не универсальная shell-команда |
| Озвучивание и слово активации | Отдельные голосовые модули; не смешивать с управляющим циклом |
| Исследование | Сначала поиск/источники и права доступа; затем инструмент в ядре |
| iPhone или backend в WSL | Новый клиент/транспорт с аутентификацией; это отдельный этап |

При новом действии сначала определяем его аргументы, ограничения и подтверждение, затем пишем обработчик и тесты. Не нужно переписывать всё приложение для каждой новой команды.

## Проверенные границы

Сборка, автономные тесты и инициализация WPF проверяются `verify.ps1`. Тесты подтверждают правила и HTTP-контракт на подставных ответах, **не качество реальной модели**, акустику микрофона или доступность Groq в аккаунте. Открытие цели означает передачу команды Windows, а не доказательство, что окно уже полностью загрузилось.

HTTP-схема сверена с официальными источниками: [чат и параметры](https://console.groq.com/docs/api-reference), [локальный tool calling](https://console.groq.com/docs/tool-use/local-tool-calling), [speech-to-text](https://console.groq.com/docs/speech-to-text).
